About Microsoft Graph permissions

Microsoft Graph supports delegated access and app-only access. The same permission name can have a delegated scope and an application app role, with separate IDs and descriptions. This catalogue also preserves resource-specific consent entries from the reference. It does not show whether consent has been granted in your tenant.

Delegated, application and resource-specific

  • Delegated permissions are used when a user is signed in. The effective access is the intersection of the permission and what that user is already allowed to do, so a delegated User.ReadWrite.All still cannot edit a user the signed-in account has no rights over.
  • Application permissions are app roles used without a signed-in user. Standard Graph application permissions require administrator consent. Endpoint-specific restrictions and resource scoping can still affect access.
  • Resource-specific consent (RSC) is a separate consent model for particular resources. RSC can have delegated or application access modes, but this dataset does not classify those modes or store a comparable admin-consent flag. Consult the RSC guidance for consent rules and supported modes.

Understanding the consent flag

Admin consent required is a property of a specific delegated or application variant, not a blanket property of the name. Selecting a type makes the consent filter apply to that type only. With All types, it matches names where at least one standard variant is marked as requiring admin consent; RSC does not supply this flag here.

When a type is selected, text search uses the permission name, resource and that variant's GUID and descriptions. Details still show the available variants together so their descriptions can be compared.

A delegated flag marked not required does not guarantee that users can consent: tenant policies can restrict user consent. Missing flags are shown as not recorded, never as no consent required. See Microsoft's permissions and consent overview.

Permissions are not Entra ID roles

Graph OAuth scopes and application permissions are distinct from Entra ID directory roles. Some endpoints require both API permissions and an appropriate role or resource assignment. Check the endpoint's documented requirements; an authorization failure can have several causes and this reference cannot diagnose a tenant's access.

Choosing the least privileged permission

  • Prefer the narrowest permission a call accepts; each Graph API method documents its own least privileged option.
  • Prefer delegated over application whenever a user is present, so the user's own limits still apply.
  • The .All suffix signals broad resource coverage, but the selected access type and endpoint-specific restrictions still matter. Read the corresponding description rather than inferring access from the name alone.
  • Keep the delegated and application GUIDs distinct when configuring permissions. OAuth scope parameters use the names or scopes required by the flow, not an arbitrary permission GUID. Check the relevant registration, consent or RSC manifest documentation.

Where this data comes from

The refresh workflow collects Microsoft's public permissions reference, including its descriptions and RSC entries. Last refreshed is the dataset timestamp. Counts describe unique permission names and overlapping type memberships; the original names and GUIDs are preserved.
