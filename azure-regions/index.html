About Azure regions

The physical regions returned for the scanning subscription, supplemented by Microsoft's public-region reference. A missing field is not a negative finding; the catalogue is not a guarantee that a service or SKU can be deployed by every subscription.

Sources and confidence by attribute
Name, ID and location type
Reported by the ARM locations API. The directory includes Physical entries; Logical entries are counted separately.
Location, coordinates and geography
Reported by ARM metadata. Coordinates are regional approximations, not datacenter addresses. Continent groups are derived locally from the reported geography group.
Availability zones
A non-empty location.availabilityZoneMappings confirms support for the scanning subscription. Otherwise the Microsoft Learn public-region reference supplies a positive zone count or explicit N/A. An absent, empty or unrecognized value remains unknown.
Preview status
Shown only when Microsoft Learn annotates the availability-zone column. One or more zones may be in preview; confirm service-specific availability before deployment.
Access restrictions
Based on the restriction marker in the region's own Microsoft Learn column, not its paired region and not ARM's Recommended/Other category. No marker means no restriction listed there, not guaranteed subscription access.
Paired region
Reported by ARM metadata. No reported pair does not establish a disaster-recovery recommendation. Read the distinction between pairs and zones.
Collection dates
ARM metadata and the public reference have separate check dates above. Neither date promises that an Azure service has completed its rollout.

Choosing a region

  • Data residency — a geography is the boundary most compliance requirements are written against.
  • Latency — the closest region to your users usually matters more than any other factor.
  • Service availability — not every service or VM family exists in every region, and previews are typically limited to a handful.
  • Price — the same resource can differ noticeably in cost between regions.
  • Capacity — popular regions can refuse specific VM sizes at times, which is worth testing before committing.

Pairs and zones are not the same thing

Availability zones protect against a datacenter failure inside one region; a regional pair supports recovery from the loss of an entire region, and governs how some platform-managed replication and sequenced updates behave. A resilient design usually needs both, and a pair is not automatically the region you would choose for disaster recovery — check latency and service parity first.
